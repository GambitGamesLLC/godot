GDGS / Godot investigation visual map

This page explains the current state of the GDGS compositor crash investigation in plain English. It is aimed at a technically literate reader who does not already know Godot rendering internals. The short version: the first bad event still appears to be the GDGS projection dispatch, but the later Vulkan failure becomes visible on a bigger frame submission called submit_serial=9.

Current first bad stage: GDGS projection_only Current failing backend submit: submit_serial=9 First meaningful pass-scope seam: Tonemap (L87) (Draw) Later heavier scope: Command Graph (L88) (Draw)

1) Simplified frame pipeline map

Stage A

GDGS compositor callback enters

Godot calls into the GDGS compositor effect during frame rendering. The callback itself can survive when no real GDGS compute work is done.

Stage B

GDGS projection dispatch

The first real compute pass. This is currently the first meaningful stage that makes the later failure inevitable.

Stage C

Projection returns to Godot

Tracked GDGS-side resources still look stable here. The callback returns through the no-writeback gate.

Stage D

Vulkan queue submit submit_serial=9

The first suspicious backend transition after the stable return seam. It is the frame-1 main submission that waits on the transfer-worker handoff.

Stage E

Frame-1 command graph runs

This submission contains a long copy-heavy body, then a short late tail of render/compute/draw scopes.

Stage F

fence_wait_error submit_serial=9 wait_result=-4

The GPU/driver reports that waiting for submit 9 failed. This is the first explicit backend failure point we can see.

Stage G

Later lost-device breadcrumb: BLIT_PASS

Once the device is already lost, later breadcrumbs collapse to BLIT_PASS. That is a later symptom, not the earliest proven cause.

GDGS projection-specific seam
Vulkan/backend failure visibility point

2) Where GDGS projection sits

The investigation repeatedly showed that callback_only and prepared_no_dispatch survive, while projection_only is the first stage that fails. That means the bug is not “the compositor callback exists” and not “any compute dispatch here is cursed.” A real scratch-only compute dispatch was later proven safe. The first bad seam is specifically the GDGS projection lane or fallout triggered by it.

Plain English: the machine can enter the compositor callback and can even do a tiny known-good compute job. The trouble starts when GDGS runs its real projection workload.

3) Where submit_serial=9 fits

After projection returns, Godot submits later frame work to Vulkan. The critical chain is:

transfer worker → submit_serial=8 signals semaphore
frame-1 main submission → submit_serial=9 waits on that semaphore
later fence wait on submit_serial=9 fails

The semaphore handoff itself looks coherent; the current evidence does not point to stale or reused semaphore ownership as the primary problem.

4) Pass-scope seam map inside failing submit_serial=9

The engine-side instrumentation progressively demoted several scary-looking scopes into empty wrappers. That matters because it tells us where the first real workload seam survives.

Render Depth Pre-Pass (L15) (Draw)

Status: demoted to empty wrapper
  • Acts as a render_pass_wrapper.
  • Shows begin/end render-pass commands, but no direct draw payload, no pipeline binds, and no nested labeled payload at this seam.

Render Opaque Pass (L16) (Draw)

Status: demoted to empty wrapper
  • The next neighboring pass after L15.
  • Still wrapper-only in the inspected command summary.

Render 3D Transparent Pass (L86) (Draw)

Status: demoted to empty wrapper
  • Still part of the wrapper-only chain.
  • Not the first surviving meaningful pass-scope workload.

Tonemap (L87) (Draw)

Status: first meaningful surviving pass-scope seam
  • Classifies as draw_payload.
  • Small but real workload: one draw call, one pipeline bind, one uniform bind.
  • This is the first pass scope that still carries direct local payload after the wrapper chain ends.

Command Graph (L88) (Draw)

Status: next heavier meaningful scope
  • Also draw_payload, but materially heavier than Tonemap.
  • Observed with many draw calls and more binding activity.
  • Good contrast point: Tonemap is the first surviving seam; L88 is the next larger meaningful workload.

5) What does fence_wait_error submit_serial=9 wait_result=-4 mean?

Plain English: Godot asked Vulkan, “has that batch of GPU work finished yet?” Vulkan answered with a device-lost error instead of “yes” or “still waiting.” In practice, that means the GPU/driver considers something in that submission path unhealthy enough that the device is no longer trustworthy.
  • submit_serial=9 = the ninth tracked queue submission in this run, specifically the frame-1 main submission after projection returns.
  • fence_wait = CPU waiting for that GPU submission to finish.
  • wait_result=-4 = Vulkan device-lost error in this context.

6) What does later BLIT_PASS mean?

Plain English: once the GPU device is already lost, later breadcrumb logging only tells us where the engine happened to notice the wreckage. BLIT_PASS is the last breadcrumb the system still remembered, not proof that the original bug started there.
  • It is a late symptom marker.
  • It does not contradict the earlier projection-first finding.
  • It also does not override the newer seam work showing the first meaningful surviving pass-scope payload at Tonemap.

7) Current best mental model

Simplified

  • GDGS projection is still the earliest proven bad stage.
  • The handoff back into Godot looks stable at the tracked resource/snapshot seam.
  • The first explicit backend failure becomes visible when Godot later waits on Vulkan submit 9.
  • Several intermediate scary-looking pass scopes turned out to be empty wrappers.
  • The first meaningful surviving pass-scope seam after those wrappers is Tonemap.

Technical

  • projection_only is the first failing staged boundary; scratch-only compute is safe.
  • Tracked projection-owned resources stayed stable through render_for_compositor_sync_snapshot.
  • submit_serial=8 is the transfer-worker handoff; submit_serial=9 is the waiting frame-1 main submission.
  • The failing command buffer is copy-heavy overall, but pass-scope inspection demoted L15/L16/L86 into wrappers.
  • Tonemap (L87) (Draw) is the first surviving pass-scope workload; Command Graph (L88) (Draw) is the next heavier one.

8) Why this page exists

The investigation has accumulated a lot of precise but easy-to-lose detail. This map compresses the current state into one durable picture: GDGS projection is still the first bad stage, submit_serial=9 is where the later Vulkan failure becomes visible, several pass scopes were demoted as empty wrappers, and the first meaningful surviving pass-scope seam is now Tonemap (L87) (Draw).
